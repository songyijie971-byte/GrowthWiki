# GrowthWiki 使用说明

这份说明用于提醒自己：这个知识库怎么用、Claude Code 怎么接入、Obsidian 里的知识图谱是什么。

## 1. 一句话用法

把 PDF/DOCX 放进 `00_Inbox/raw/`，在 `00_Inbox/intake.md` 登记，然后让 Claude Code 处理。

最短指令：

```text
处理 intake 里的全部待处理资料，按 CLAUDE.md 执行。
```

只处理第一条：

```text
处理 intake 里的第一条。
```

查询知识库：

```text
基于 D:\GrowthWiki 本地 Markdown 知识库回答。回答时区分 Knowledge Base、Inference、Missing，知识库没有的不要编造。
```

## 2. 日常资料进入流程

1. 把原文放入 `00_Inbox/raw/`。
2. 在 `00_Inbox/intake.md` 新增一行，状态写 `待处理`。
3. 让 Claude Code 处理 intake。
4. Claude Code 生成结构化 Markdown：
   - 论文/文献 -> `01_Papers/`
   - 技术文档 -> `02_TechDocs/`
   - 项目技术资料 -> `04_Projects/`
5. Claude Code 提取概念并链接到 `03_Concepts/`。
6. Claude Code 更新 `99_Maps/` 里的 map 页面。
7. 在 Obsidian Graph View 里查看默认核心图谱。

## 3. Obsidian 与 GitHub 同步

GrowthWiki 的同步链路是：

```text
Obsidian 本地知识库 -> Git 版本管理 -> GitHub 云端备份
```

在 `D:\GrowthWiki` 中完成笔记修改后，提交并推送：

```powershell
Set-Location D:\GrowthWiki
git add .
git commit -m "update notes"
git push
```

如果这次主要更新 ROS 2 笔记，可以使用更具体的提交说明：

```powershell
git add .
git commit -m "update ROS2 notes"
git push
```

换电脑，或另一台电脑也修改过这个知识库时，先同步远端历史，再提交本地修改：

```powershell
Set-Location D:\GrowthWiki
git pull --rebase
git add .
git commit -m "update notes"
git push
```

这样每次修改都会保留 Git 历史，除了 GitHub 备份外，还可以在需要时回看或恢复之前的版本。

## 4. 每个目录的作用

- `00_Inbox/`：临时入口，不是长期知识层，不进入默认图谱。
- `00_Inbox/raw/`：临时放 PDF/DOCX 原文。
- `01_Papers/`：论文/文献整理笔记，进入默认图谱。
- `02_TechDocs/`：技术文档整理笔记，进入默认图谱。
- `03_Concepts/`：连接论文和技术文档的概念页，进入默认图谱。
- `04_Projects/`：项目技术沉淀，按需查看，不进入默认图谱。
- `05_Graph/`：Obsidian 图谱说明和过滤器，不进入默认图谱。
- `99_Maps/`：人和 Claude Code 的导航入口，不进入默认图谱。

## 5. 知识图谱是什么

你之前说的“知识图谱”，在这个库里主要指 Obsidian Graph View 看到的节点和连线。

它不是单独的数据库，也不是自动生成的向量库。

整个文件夹都是 GrowthWiki 知识库，但默认 Graph View 只看真实知识节点：`01_Papers/`、`02_TechDocs/`、`03_Concepts/`。

`README.md`、`CLAUDE.md`、`AGENTS.md`、模板、map、图谱说明是维护节点，不是默认知识图谱节点。

在 Obsidian 里：

- 一个 Markdown 文件就是一个节点。
- 一个 Obsidian 双链就是一条边。
- 论文笔记、技术文档笔记、概念页会形成默认网络。
- 概念页是最重要的桥接节点。

典型结构：

```text
技术文档_A -> 概念_X <- 论文_B
                    ^
                    |
                 项目_C
```

当前 GrowthWiki 的结构会长成：

```text
02_TechDocs/技术文档
    -> 03_Concepts/概念页
        -> 未来的 01_Papers/论文笔记
        -> 未来的 04_Projects/项目页
```

## 6. 你发的图对应什么

你发的截图里，圆点是知识节点，线是节点之间的关系。

放到 GrowthWiki 里可以这样理解：

- 中间的大节点：可能是一个核心项目、核心概念或主地图。
- 周围的小节点：论文、技术文档、概念、项目。
- 连线：Markdown 里的 Obsidian 双链。
- 节点越中心，通常说明它被更多页面链接。

GrowthWiki 不追求一开始就长成密集大图。正确方式是随着真实文档进入，图谱自然变密。

## 7. Obsidian 里怎么看图谱

打开 Obsidian 后：

```text
Ctrl + P -> Open graph view
```

推荐过滤器：

```text
(path:01_Papers OR path:02_TechDocs OR path:03_Concepts) -path:README -path:paper-template -path:techdoc-template -path:concept-template -path:concept-map
```

用途：默认只显示论文笔记、技术文档笔记、概念页。

默认不显示：

```text
00_Inbox
05_Graph
99_Maps
README
CLAUDE
AGENTS
paper-template
techdoc-template
concept-template
concept-map
```

用途：避免维护节点污染知识图谱。

```text
path:02_TechDocs OR path:03_Concepts
```

用途：查看当前技术文档和概念的连接。

以后论文多了，仍然用默认核心过滤器：

```text
(path:01_Papers OR path:02_TechDocs OR path:03_Concepts) -path:README -path:paper-template -path:techdoc-template -path:concept-template -path:concept-map
```

## 8. 怎么判断图谱质量

好的图谱：

- 每篇论文链接 2-5 个具体概念。
- 每篇技术文档链接 1-3 个具体概念。
- 技术文档节点名短、稳定，表达知识主题。
- 概念页能连接多篇资料，而不是孤立页面。
- 项目页能连接相关论文、技术文档和概念。
- Map 页面能帮助人和 Claude Code 快速进入知识库。

不好的图谱：

- 为了好看创建空概念页。
- 创建过泛概念，例如 `概念_AI`、`概念_技术`、`概念_论文`。
- 直接把公众号长标题当成文件名。
- 只有目录链接，没有真实知识关系。
- PDF/DOCX 原文没有编译成 Markdown。

## 9. 给 Claude Code 的常用指令

处理资料：

```text
处理 intake 里的全部待处理资料，按 CLAUDE.md 执行。
```

检查链接：

```text
检查 03_Concepts 里的概念页，把“在知识库中的连接”部分里的论文、技术文档、项目名称改成 Obsidian 双链。不要新增空页面，不要改正文含义。
```

查询知识：

```text
基于 D:\GrowthWiki 本地 Markdown 知识库，回答：某个概念和哪些论文、技术文档、项目有关？

请优先读取 99_Maps/index.md、03_Concepts/concept-map.md、01_Papers/、02_TechDocs/、04_Projects/。
回答分成 Knowledge Base、Inference、Missing。
```

检查图谱质量：

```text
检查当前知识库的双链质量：是否有空概念页、孤立页面、过泛概念、断链，以及哪些页面应该补充 cross-link。
```

## 10. 最重要的原则

- PDF/DOCX 是原料，不是长期知识。
- Markdown 笔记才是长期知识。
- 双链负责关系。
- 概念页负责桥接。
- Map 页面负责导航，不进入默认图谱。
- Graph View 是自然结果，不是造页面的理由。
